# SUMMARY — fix taskmux tmux-grimoire popup (branch `fix-taskmux-grimoire`)

## Symptom

The `tmux-grimoire` popup bound to `Ctrl+t` (running `taskmux list`) opened
for a brief moment and immediately closed.

## Root cause

1. tmux executes a `display-popup` command string by invoking the session's
   `default-shell` as `default-shell -c <command>` (confirmed in tmux source:
   `popup.c` uses `job_run(..., JOB_DEFAULTSHELL)`, and `job.c` does
   `execl(shell, argv0, "-c", cmd)`).
2. The deployed tmux on this machine is the "tmuxed" devshell variant built by
   `sandyFireworksBus/tmuxifyDevShell.nix`, which overrides `default-shell`
   with the wrapper generated by
   `sandyFireworksBus/shellScriptOfDevshell.nix`.  For the `sieyesShell` /
   `headless` devshells that wrapper ends in `exec nushell "$@"`
   (`postShellHookInteractiveShell = nushell`).
3. nushell cannot execute POSIX sh command strings.  The grimoire popup
   command is
   `tmux select-window -t '...' \; attach-session -t '_shpell-session' \; run-shell '...'`.
   Under nushell it fails to parse (`nu -c` reproduces the failure), exits
   immediately, and — because grimoire opens the popup with `display-popup -E`
   ("close when the command exits") — the popup closes instantly.

Verified empirically on the real server: a popup command
`echo hi > /tmp/file` produced no file (nushell treats `>` as an argument),
while wrapping the same command in `sh -c "..."` worked.

## Fix

`sandyFireworksBus/shellScriptOfDevshell.nix`: the generated devshell wrapper
now detects the one-shot command invocation mode (`$0 -c <command>`) and
delegates it to `bash`, which implements the POSIX semantics tmux and other
callers expect.  Interactive sessions still get the configured shell
(nushell), and `-c` commands still run inside the devshell environment.

This fixes tmux-grimoire's popup *and* any other popup-style command (e.g.
tmux-palette's popup job) for both tmuxed devshells (`sieyesShell-tmuxed`,
`headless-tmuxed`).  Nothing was committed, per instructions.

## Testing

1. **Local functional test (isolated socket, separate from the host server).**
   Built the fixed tmuxed tmux from the working tree and drove a real pty
   client with a Python harness: pressed `Ctrl+t`, observed the popup draw and
   stay open for the whole 8 s observation window (`_shpell-session` remained
   attached, popup border + `| taskmux-list` title rendered repeatedly).
2. **VM visual test (tmux inside a tmux session inside the VM console).**
   Built the `tmux-console-vm` NixOS VM against the fixed tree, with the VM's
   tmux being the tmuxed (nushell `default-shell`) variant — the exact
   configuration in which the bug manifested.  Drove it over the serial
   console, triggered the exact command the `C-t` binding runs, and verified:
   - `_shpell-session` (the popup's session) reports `attached 1` — the popup
     is open;
   - it is *still* attached 6+ seconds later — it no longer closes
     immediately;
   - QMP screendumps of the VGA console show the popup rendered on the tmux
     session's console, including the interactive `taskmux list` menu
     (`❯ work: underway - fix-the-grimoire-popup`,
     `j/k: move, Return: switch, q: quit`).
   Screenshots (in the repo root, uncommitted):
   - `vm-console-popup-open.png` — popup open on the VM console
   - `vm-console-popup-early.png` — popup seconds later, still open
   - `vm-console-popup-taskmux-list.png` — popup showing the `taskmux list` menu

## Incident note

During earlier diagnosis, a test harness passed an empty `TMUX` environment
variable to a `tmux kill-server` invocation without an explicit `-L` socket,
which hit the *default* socket and killed the host's real tmux server.  This
destroyed the user's live sessions (no tmux-resurrect snapshot existed, so
they were unrecoverable).  All subsequent tmux usage was restricted to
explicitly-named test sockets, verified with `list-sessions` before any
destructive command, and the final visual test runs tmux entirely inside a
QEMU guest.
